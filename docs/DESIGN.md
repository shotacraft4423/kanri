# 販売管理アプリ 設計書 (kanri)

個人事業・小規模販売向けの商品・仕入れ・在庫・売上・発送・顧客管理を、
サーバー契約なしでスマートフォン単体（オフライン）で完結させるアプリの設計。

---

## 1. システム構成

- **技術選定: Flutter (Dart) 単一コードベースで Android / iOS 両対応**
  - 理由: ローカルDB暗号化(SQLCipher)・生体認証(local_auth)・セキュアストレージ(Keychain/Keystore)・
    ファイルI/O・オフライン動作のいずれも成熟したプラグインが揃っており、UIを1実装で両OSに配布できる。
- **サーバーレス構成**: バックエンドサーバー・自社API・クラウドDBを持たない。
  ネットワークが必要なのは「追跡番号タップで配送会社サイトを開く」等の任意機能のみ。
- **レイヤー構成**
  ```
  UI (features/*)            … 画面・状態管理 (Riverpod)
  Repository層 (repositories) … ユースケース単位のデータ操作・業務ロジック呼び出し
  Core:
    core/db      … SQLCipher接続・スキーマ・マイグレーション
    core/security … 認証(生体/PIN)・自動ロック・スクリーン保護・鍵管理
    core/pricing  … 仕入原価計算・価格帯(×1/×3/×5)・利益計算
    core/backup   … CSV出力・暗号化フルバックアップ・インポート差分プレビュー
    core/audit    … 監査ログ記録
  Models (models) … Product / Supplier / Purchase / PurchaseItem / Inventory /
                     InventoryAdjustment / Customer / Order / OrderItem /
                     Shipment / PriceHistory / AuditLog / AppSettings
  ```

## 2. データモデル（要点）

セクション37の全テーブルに加え、平均原価管理用に `ProductCost` を追加。
主キーはすべてアプリ内生成のUUID文字列（複数端末間での将来的な統合を考慮）。

| テーブル | 役割 | 履歴不変の要点 |
|---|---|---|
| products | 商品マスタ（現在価格・現在庫参照用ではなく商品属性のみ） | 価格変更は`price_history`に記録、過去注文の単価には波及しない |
| suppliers | 仕入先マスタ（現状1件、複数対応可能な構造） | - |
| purchases | 仕入れ発注ヘッダ（ステータス・追跡番号・到着日） | - |
| purchase_items | 仕入れ明細（商品・数量・商品代/送料/手数料/調整額/実支払額/入荷済み数量） | 入荷済み数量で二重加算防止 |
| product_cost | 商品ごとの移動平均原価（入荷のたびに更新） | 過去の販売原価は`order_items.unit_cost`に固定済みなので不変 |
| inventory | 商品ごとの現在庫（数量・予約数） | 入荷/販売/在庫調整の都度、単方向に増減 |
| inventory_adjustments | 手動在庫調整履歴（理由・メモ） | 追記のみ |
| customers | 顧客情報（氏名・郵便番号・住所・電話・メモ） | 機密情報。一覧非表示・詳細のみ表示 |
| orders | 販売ヘッダ（注文番号・販売日・顧客・メモ） | - |
| order_items | 販売明細（数量・単価・価格帯・原価スナップショット・利益） | 販売時点の単価・原価を凍結して保存（商品マスタ変更の影響を受けない） |
| shipments | 発送情報（注文と1:1、ステータス・追跡番号・発送日・到着日） | - |
| price_history | 価格変更履歴 | 追記のみ |
| audit_logs | 主要操作の変更履歴（誰が・いつ・何を・before/after） | 追記のみ |
| app_settings | アプリ設定（原価計算方式・自動ロック時間・通知ON/OFF等） | - |

## 4. 画面遷移（概要）

```
起動 → ロック画面（生体認証 or PIN） → ホーム
ホーム → [発送待ちバッジ] → 発送一覧(未発送タブ)
ホーム → [仕入れ待ちバッジ] → 仕入れ一覧(未到着タブ)
ホーム → 商品/仕入れ/在庫/販売/発送/顧客/履歴/集計/設定 の各タブ

商品一覧 → 商品編集 → 保存(価格変更時price_history追記)
仕入れ一覧 → 仕入れ登録 → 追跡番号登録 → 入荷処理 → 在庫反映
在庫一覧 → 在庫調整(理由入力) → audit_logへ記録
販売登録 → 商品選択 → 数量/価格帯選択 → 顧客選択/新規登録 → 確定 → 在庫減算 → 発送(未発送)生成
発送一覧 → 発送準備 → 追跡番号入力 → 発送済み → 配送中 → 配達完了
顧客一覧(マスキング) → 顧客詳細(生体/PIN再確認は起動時のみ、詳細表示自体は都度は求めない設計)
設定 → バックアップ/エクスポート/インポート、セキュリティ設定、データ初期化(二重確認)
```

## 5. セキュリティ設計

1. **起動時認証**: アプリ起動直後は必ずロック画面。生体認証(local_auth)を第一選択、
   非対応/未設定/失敗時はアプリ専用PIN（端末ロック解除PINとは完全に別物）。
2. **PIN保管**: 平文保存しない。ランダムsalt + PBKDF2(またはArgon2相当)でハッシュ化し、
   `flutter_secure_storage`（iOS Keychain / Android EncryptedSharedPreferences+Keystore）に保管。
   DB内には一切保存しない。
3. **DB暗号化鍵**: アプリ初回起動時に256bitランダム鍵を生成し、`flutter_secure_storage`にのみ保管。
   SQLCipherのpassphraseとして使用し、DBファイル自体を全面暗号化。鍵はOSのセキュアストレージ任せで、
   アプリ側でハードコードしない。
4. **端末ロック解除だけでは中身を見られない**: OSレベルの生体/PINとアプリ内認証は独立。
   端末を貸してロック解除されても、アプリ内に入るには別途アプリの生体認証 or PINが必要。
5. **自動ロック**: 設定した無操作時間経過、またはバックグラウンド遷移で自動的に再ロック
   （タイミングは設定画面で「起動時のみ/バックグラウンド復帰時/一定時間経過後」を選べる）。
6. **アプリ切替画面対策**: `screen_protector`パッケージ + ネイティブ設定で
   Androidは`FLAG_SECURE`、iOSはバックグラウンド遷移時にプライバシー用オーバーレイ（ぼかし）を表示し、
   タスクスイッチャーのサムネイルに機密情報が写らないようにする。iOSはOS仕様上スクリーンショット自体は
   ブロックできないため「防止を試みるが完全阻止は保証しない」ことを明記。
7. **PINリセット非提供**: PINを忘れた場合の「簡易再発行」は実装しない。復旧するには
   （ユーザー主導の）暗号化バックアップからの復元のみとし、開発者が復号できる抜け道は作らない。
8. **エクスポート/バックアップの暗号化**: 顧客情報を含む完全バックアップは
   ユーザー指定パスワードを鍵導出(PBKDF2)し、AES-256-GCMで暗号化した単一ファイルとして出力。
   通常のCSV出力（商品・仕入れ・売上集計等の汎用データ確認用）は顧客個人情報列を含めない、
   または明示同意の上でのみ出力する。
9. **ログ非記録**: 顧客氏名・住所・電話番号・追跡番号等を`print`/ログに出力しない
   （監査ログはDB内にのみ、アプリ内画面からしか閲覧不可）。
10. **外部送信なし**: 解析SDK・広告SDKは導入しない。ネットワーク通信は「追跡番号から配送会社サイトを開く」
    ブラウザ起動のみに限定する。

## 6. データ保存方式

- SQLCipher暗号化SQLite（`sqflite_sqlcipher`）を唯一の永続化先とする。
- アプリ専用ディレクトリ（`path_provider`の`getApplicationDocumentsDirectory`)配下に配置し、
  他アプリからアクセス不可（OSのサンドボックスに依存）。
- 添付ファイル等バイナリは現時点で扱わない（将来の商品画像機能はセクション36で対応予定）。

---

## 7. バックアップ方式

- **エクスポート**: ①暗号化フルバックアップ(.kanribackup, AES-256-GCM, パスワードはユーザー指定・
  端末非保存) ②汎用CSV（商品/仕入れ/販売/在庫/発送、顧客個人情報列は既定でマスク）。
- **インポート**: 暗号化バックアップを復号後、既存データとID突合（UUID一致で更新、
  未存在は新規追加、商品参照が欠落しているレコードは競合として提示）し、
  「新規○件 / 更新○件 / 競合○件」をプレビュー表示してからユーザー確定操作で反映。
- 自動クラウド送信は行わない。明示的な「エクスポート」操作でのみファイル生成。

---

## 8. 在庫計算方式

- `inventory.quantity` はイベントソース的に増減のみで管理（直接編集はしない）。
- 増加要因: 入荷処理（`purchase_items.received_quantity`の差分適用、同一明細の再入荷処理は
  「新しい入荷数量 − 既存入荷数量」の差分のみ反映するため二重加算されない）。
- 減少要因: 販売登録（`order_items`確定時に即時減算）。
- 手動調整: `inventory_adjustments`に理由付きで記録し、`quantity`に加減算（マイナス在庫は警告表示）。
- 在庫僅少/在庫切れ判定: `quantity <= 0` → 在庫切れ、`0 < quantity <= low_stock_threshold` → 残りわずか。

---

## 9. 利益計算方式

- 原価計算方式は`app_settings`で切替可能な構造とし、初期値は**移動平均原価法**。
  - 入荷確定のたびに `product_cost` を
    `avg = (旧累計原価 + 今回受領分のactual_paid) / (旧累計数量 + 今回受領数量)` で更新。
- 販売確定時、その時点の`product_cost.avg_unit_cost`を`order_items.unit_cost`にスナップショットし、
  `profit = line_total - unit_cost * quantity`（必要に応じ配送関連費用を控除）を保存。
  以降、商品マスタや原価が変わっても過去の`order_items`の値は不変。
- 将来のFIFO対応は、原価計算戦略をインターフェース化（`CostStrategy`）しておき、
  `product_cost`に加えFIFO用の入荷ロット別残高テーブルを追加すれば拡張できる設計とする。

## 10. ステータス設計

**仕入れステータス**: 発注前 → 発注済み → 発送済み → 配送中 → 到着 → 入荷処理済み（/ キャンセル）
**発送ステータス**: 未発送 → 発送準備中 → 発送済み → 配送中 → 配達完了（/ 保留 / キャンセル）
**在庫状態(表示用)**: 正常 / 残りわずか / 在庫切れ
**在庫調整理由**: 棚卸し / 破損 / 紛失 / 入力ミス修正 / その他

いずれも列挙型で管理し、ステータス変更はユーザーの手動操作（ボタン/選択）で行い、
発送済みへの変更時は発送日を必須で記録するなど、状態遷移に伴う必須項目をUIでバリデーションする。

## 開発者判断事項（合理的に決定した細部）

- 注文番号・仕入れIDの採番は `YYYYMMDD-連番` の人間可読フォーマットとし、内部主キーは別途UUIDを保持。
- 価格帯は既定で×1/×3/×5だが、販売登録画面では任意数量+単価上書きも可能とする（現場の柔軟性を優先）。
- 顧客情報の「一覧でのマスキング」は氏名の一部伏字＋住所非表示とし、詳細画面タップで全表示する
  （詳細画面表示自体に都度生体認証は要求しない。要求するとseconds単位の頻繁操作で実用性が落ちるため、
  代わりにアプリ全体のロック/自動ロックで担保する）。
- CSVエクスポートは既定で顧客個人情報列（氏名・住所・電話）を含めない。含める場合は
  エクスポート画面で明示的にチェックを入れさせ、確認ダイアログを出す。
- 監査ログの対象操作: 価格変更・在庫調整・販売登録/キャンセル・仕入れ登録/変更・発送ステータス変更・入荷処理。
- データ初期化は設定画面の最下部、専用の確認画面（アプリ名の入力を要求）を経由しないと実行できない。
- 通知は端末ローカル通知（`flutter_local_notifications`相当を将来追加）を想定し、
  初期実装では設定のON/OFFフラグとアラート条件判定ロジックのみ用意し、実際のプッシュ配信は
  次段階で結線する（サーバー不要のローカル通知のみで完結させる方針）。
- iOSのスクリーンショット自体は技術的にブロックできないため、「アプリ切替時のプレビュー保護」
  「画面録画検出時の警告表示」までを実装範囲とし、その旨を利用者に明示する。

## 実行環境に関する制約事項

本セッションの実行環境には Flutter SDK がインストールされていないため、
`flutter create` によるネイティブ (`android/` `ios/`) プロジェクトの自動生成、
および `flutter pub get` / `flutter analyze` / 実機・エミュレータでのビルド確認ができていません。
`lib/` 以下のDartソースコードと `pubspec.yaml` は作成済みです。
実際に動かす際は `docs/SETUP.md` の手順に従ってプラットフォームプロジェクトを生成し、
セキュリティ関連のネイティブ設定を追加してください。
